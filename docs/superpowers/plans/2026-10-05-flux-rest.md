# Flux REST Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Im Portal einen verschlüsselten Flux-Zugang sowie Abgleich und gezielte Anlage von SKR04-Sachkonten bereitstellen.

**Architecture:** Ein Flux-Client kapselt HTTP und Antwortprüfung. Fachliche Actions speichern Zugangsdaten und Sachkonten; Livewire-Komponenten zeigen die bestehende Schnittstellenseite und eine neue Sachkontenseite. Die vorhandene Registrar-Schnittstelle bleibt kompatibel.

**Tech Stack:** PHP 8.4, Laravel 13, Livewire 4, TallStackUI 3, MariaDB, Pest 4, Laravel HTTP Client.

**Spec:** `docs/superpowers/specs/2026-10-05-flux-rest-design.md`

## Global Constraints

- Laravel 13, PHP 8.4, klassenbasiertes Livewire 4.
- Token wird maskiert eingegeben, verschlüsselt gespeichert und nie vorbefüllt, in Meldungen oder Logs ausgegeben.
- Nur HTTPS, keine Zugangsdaten im URL, keine Query-/Fragmentbestandteile.
- Keine automatischen Wiederholungen von POST-Anfragen.
- Vorhandene Flux-Konten werden nicht still umbenannt, gelöscht oder steuerlich umkonfiguriert.
- Diese erste Umsetzung erstellt keine Rechnungen, bucht keine Belege und versendet keine E-Mails.
- Tests verwenden MariaDB und HTTP-Fakes, keine produktiven Schreibanfragen.

## Review Focus

- Basisadresse mit abschließendem Slash darf nicht zu `/api/api` führen; fremde Hosts und Redirects dürfen keinen Token erhalten (Task 1).
- Unvollständige oder wiederholte Pagination darf keinen scheinbar vollständigen Abgleich erzeugen (Task 1).
- Zwei Mandanten mit identischen Nummern dürfen nicht miteinander verknüpft werden (Task 2).
- Erfolgreicher POST mit verlorener Antwort darf bei Wiederholung kein zweites Konto erzeugen (Task 2).
- Öffentliche Livewire-Methoden müssen Gastzugriffe und manipulierte Provider/Typwerte zurückweisen (Task 3).

```php
return Cache::lock('flux-ledger:'.$client->tenantId().':'.$input['number'], 120)
    ->block(5, function () use ($client, $input, $userId) {
        $matches = collect($client->ledgerAccounts())->where('tenant_id', $client->tenantId())->where('number', $input['number']);
        if ($matches->count() > 1) {
            throw new FluxException('Mehrere Flux-Konten haben diese Nummer. Bitte den Bestand prüfen.');
        }
        $existing = $matches->first();
        if ($existing && $existing['ledger_account_type_enum'] !== $input['type']) {
            throw new FluxException('Diese Kontonummer ist in Flux mit einem anderen Kontentyp belegt.');
        }
        $remote = $existing ?? $client->createLedgerAccount([
            'tenant_id' => $client->tenantId(), 'number' => $input['number'],
            'name' => $input['name'], 'ledger_account_type_enum' => $input['type'],
            'is_automatic' => $input['is_automatic'],
        ]);
        return FluxLedgerAccount::query()->updateOrCreate(
            ['provider' => 'flux', 'tenant_id' => $client->tenantId(), 'number' => (string) $remote['number']],
            ['name' => $remote['name'], 'type' => $remote['ledger_account_type_enum'],
                'is_automatic' => $remote['is_automatic'], 'flux_id' => $remote['id'],
                'chart' => 'SKR04', 'synced_at' => now(), 'updated_by' => $userId],
        );
    });
```

- [ ] Den gezeigten Ablauf um `created_by` beim ersten Insert ergänzen. Nach Timeout oder unklarer POST-Antwort einmal lesend rekonzilieren: nur exakt passender Mandant/Nummer/Typ darf übernommen werden, andernfalls sichere Meldung und kein zweiter POST. Bei Lock-Timeout ebenfalls kein POST.
